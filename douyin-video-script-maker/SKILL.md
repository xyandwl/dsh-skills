# 抖音脚本与抖音文案制作

把抖音选题、商品或服务信息、创作想法，变成一份真的能照着拍的脚本：3 个开场钩子、
逐句口播、分镜提示、字幕提示、视频标题、话题标签，以及一条评论区互动引导。脚本定稿
之后，再用它刚产出的那个选定标题渲染一张竖版封面。

## 适用范围与路线选择

口播讲解、商品演示、测评、开箱、门店介绍、店铺内容，以及持续更新的账号系列，都适用
本 Skill。它写方案和出镜语言，最后再用这份已认可的文案做一张封面。

这里的封面路线从本次对话自己的脚本出发：标题已经定了，不涉及任何参考图，产出一张图。
如果封面要从照片、关键帧、商品图或多张有序参考图出发，要比较几个不同概念，或者要在
已认可的稿子上继续精修，那属于 `douyin-cover-maker`，它从真实素材图做合成和编辑。
已定稿、需要配音音频的脚本请使用 `short-form-voiceover-audio`；要让 AI 达人拿着商品图
出镜讲解请使用 `douyin-ugc-ad-creator`；要把一张商品图做成成品视频请使用
`product-video-studio`。

## 输入与默认值

复用对话中已有的选题、商品或服务信息、目标观众、出镜风格、参考内容和期望时长。只追问
会改变脚本的信息：观众是谁、要观众做的那一个动作或记住的那一个点、素材事实、创作者的
说话风格，或者目标时长。只有一个选题也足以起草一版探索性的知识类脚本；这时要标明哪些
是假设，并且把商品主张、价格、效果、资质和优惠留给用户提供的事实。

默认给出 3 个开场钩子、一版 30–60 秒的脚本、口语化的节奏、一个明确的观众收获、
「钩子 → 证据或讲解 → 价值兑现 → 评论引导」的简单结构，以及每一段口播都配一个分镜提示。
这三个开场钩子默认按「前 3 秒决定去留」来写，不是自报家门。
用户给了时长就按这个时长来，通过调整台词密度来适配，而不是凭空给出一个关于
完播或爆款的承诺。

封面使用 2K 竖版 9:16 画幅和 `count: 1`，并省略 `model`，由它解析为 `auto`。只有当用户
点名了另一个投放位置时才改画幅，并把最终定下来的档位和比例冻结进确认里。默认是留出
文字安全区，而不是承诺把中文排印进图；用户确实要图内文字时，把那段确切的短文案写进
确认，并且只有在真的能看到结果时才逐字回读。

## 标准流程

第 1 到 6 步都不花钱，包括读卡片和给封面报价。脚本本身就是一份完整的交付物。

1. 先写简报卡：受众、要给观众的那一个价值承诺、用户提供的事实、必须保留的措辞、出镜风格、
   时长、可用的视觉素材，以及希望观众做的动作。
2. 起草 3 个明显不同的钩子，选定其中一个作为主开场，另外两个保留备用。正文围绕一个
   证据、一次演示、一个故事转折或一段有用的讲解展开，并以自然的评论引导收尾。
3. 产出逐句口播、镜头与动作提示、字幕断句、视频标题、话题标签和拍摄备注。所有说法都
   要能对应到用户提供的事实；缺少的证据点要作为问题抛回给用户，而不是用听起来合理的
   细节把它填上。
4. 复核初稿：口语流畅度、开场是否清楚、是否只讲一件事、时长、可拍摄性、字幕可读性，
   以及互动引导是否不生硬。交付主脚本，并附上没有采用的那两个钩子。
5. 脚本交付之后，免费准备封面报价：从主钩子、选定的标题和选题推导视觉方向——这条视频
   真正要讲的那个具体主体、场景和处理方式——然后读取 `text_to_image` 的实时卡片：调用
   `beatra.models.list`。用户此前已经说过不要配图时，跳过这一步和后面两步。
6. 把封面和冻结方案放在同一条消息里给出，然后停下来。说明这是付费步骤，并展示最终提示词、
   2K 9:16 画幅、`count: 1`、`auto` 会怎样解析模型、该档位的当前估价——当 `auto` 仍有多个
   模型可选时，则给出实时区间并以其上限为批准天花板——以及稳定的 `client_request_id`。
   用户不接这一步，他要的东西也已经全部拿到了。
7. 只有在用户批准了那份冻结方案之后，才调用一次 `beatra.images.generate`。用
   `beatra.tasks.get` 轮询到终态，然后交付结果。

## 需要确认的决策

只有一道付费闸门。封面和冻结方案一起给出，所以用户是在同一条消息里看到价格和那句征求
同意的话；在这份方案存在之前给出的同意，不能拿来提交任何东西。针对已经展示的方案明确
说继续，才算批准。比较选项、标题还没定、价格问题还没答，都不算。

每一次额外的 `beatra.images.generate` 都是新的付费工作，需要它自己的标识和它自己的、
展示当前价格的确认——包括结果不满意之后按原参数重摇一次这种、请求本身什么都没变的情况。
改写脚本仍然不花钱。

不要为已经交付的那张封面再付一次钱：把同一张已交付的图拿到 `douyin-cover-maker` 重渲染，
等于一张图收两次费。对已交付封面做真正的编辑是另一回事：它改变的是这张图而不是重复它，
所以交给 `douyin-cover-maker`，由它自己计价和确认。独立的封面需求——不是承接本次对话里
写出来的脚本的那种——同样路由到 `douyin-cover-maker`，即使用户手上没有任何照片。

## 执行方式

所有远程 Beatra 工具都只通过随包的 `scripts/mcp_client.py` 调用，工具名作为命令行参数，
参数以 JSON 从标准输入传入：

```text
printf '%s' '{"capability":"text_to_image"}' | python3 scripts/mcp_client.py call beatra.models.list
```

不得配置或调用宿主 Beatra Connector，也不得使用 REST/OpenAPI 作为回退。随包客户端会在
首次调用时自己完成安装注册，因此没有单独的注册子命令。给封面一个稳定的、不含用户内容的
不透明 `client_request_id`，并且只提交一次。

## 交付与复核

交付脚本、没有采用的那两个钩子，以及——当确实渲染了封面时——它的产物链接、返回的尺寸、
任务 ID、解析出的模型和 `billing.net_charged_credits`。只报告任务真正返回的内容。

能看到封面时，检查手机尺寸下主体是否清楚、标题区域是否留得干净，以及用户要求的图内文字
是否与已确认的措辞逐字一致。看不到时，说明哪些部分没有检查过，而不是把它们描述成已核验。

## 恢复

立刻记下任务 ID，并且只轮询那一个任务；`queued` 和 `running` 都表示等待。创建响应丢失时，
用同一个 `client_request_id` 重新提交那份一模一样的冻结载荷。任务 ID 丢失时，先按能力列出
任务并与自己的记录比对，然后才考虑重试。`insufficient_balance` 表示什么都没开始、也没有
扣费，充值之后可以原样重新提交同一个请求。封面失败或重做，都不会影响已经交付的脚本。

## 更新与安全

本 Skill 会自动更新。内置客户端每天最多一次从 Beatra 官网读取本渠道的版本信息
（中国大陆网络走 www.beatra.cn 与 cdn.beatra.cn）。有新版本时，它下载官方发布包，
逐个文件校验 SHA-256，再替换本 Skill 自己的文件；你放进这个目录的其他文件不会被
改动。替换过程中断时，下次运行会自动恢复到替换前的状态。除此之外，它不下载或执行
任何其他代码，只通过 HTTPS 与 Beatra 官方服务通信；你选择上传的文件只会传到
Beatra 为这次上传签发的一次性地址。

关闭自动更新：`python3 scripts/mcp_client.py update --auto off`。关闭后，客户端每天
最多提示一次在你安装它的商店里更新的命令。详见更新与安全（references/updates-and-security.md）。
